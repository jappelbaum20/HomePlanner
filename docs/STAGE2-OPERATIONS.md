# Stage 2 deployment and recovery contract

This is a local review candidate. It does not authorize execution or establish production readiness. Preserve the existing HomePlanner database, photos, lock files, private configuration, provider overlay and Caddy routes; do not touch Energy services. The active host configuration may have diverged from these repository files. Capture its current non-secret effective Compose configuration and compare every service, network, mount, image, environment path and overlay before proposing changes; do not replace it wholesale with this example.

## Private files and roles

Keep all existing file-backed settings in `compose.yaml`. In addition, supply these absolute host paths as Compose substitution variables. The files are mounted only in the listed service and are never passed as secret values through Compose environment variables:

| Host path variable | Container path | Service | Requirement |
| --- | --- | --- | --- |
| `HOMEPLANNER_ACCESS_PUBLIC_DATABASE_URL_FILE` | `/run/secrets/access_public_database_url` | web | `hp_access_public_login` URL |
| `HOMEPLANNER_MAIL_DATABASE_URL_FILE` | `/run/secrets/mail_database_url` | web | `hp_mail_worker_login` URL, required even with mail off |
| `HOMEPLANNER_ACCESS_RATE_KEY_FILE` | `/run/secrets/access_rate_key` | web | independent, persistent high-entropy key, at least 32 bytes |
| `HOMEPLANNER_ACCESS_PUBLIC_DB_PASSWORD_FILE` | `/run/secrets/access_public_db_password` | maintenance | password for the public login |
| `HOMEPLANNER_MAIL_DB_PASSWORD_FILE` | `/run/secrets/mail_db_password` | maintenance | different password for the mail login |
| `HOMEPLANNER_GMAIL_APP_PASSWORD_FILE` | `/run/secrets/gmail_app_password` | web, optional mail overlay only | separately provisioned mailbox app password |

All database URLs must target `db:5432/homeplanner`, contain the correct distinct role and its corresponding password, and have no query or fragment. URL-encode credentials when constructing a URL privately. Make the new passwords independent of one another and of the existing role passwords; use at least 32 bytes. The rate key must be distinct from auth and CSRF secrets and retained across restarts and recovery. Rotating it changes the rate-limit identity mapping; plan that separately. Never print or commit values.

Local Compose file-backed secrets retain host file ownership and permissions; `uid`, `gid` and `mode` are not reliably imposed by Compose. Provision regular non-symlink files owned by UID/GID `1000:1000`, mode `0600`, under appropriately protected, traversable host directories. For each actual mount, inspect metadata inside the running UID 1000 container and confirm the mount is read-only, the file has no group/other permissions, and its contents can be read by UID 1000 without displaying them. Verify each service receives only its required mounts: in particular, the bootstrap URL and role passwords do not belong in web. Validate the bootstrap secret separately for PostgreSQL. Keep the existing photo-volume and operations-lock inode, owners, modes and mount paths unchanged. The `operations-lock.sh` wrapper must be used for standalone maintenance jobs.

The base config sets `HOMEPLANNER_MAIL_ENABLED=0` and does not mount a mailbox credential. The optional `compose.mail.yaml` sets it to `1`, requires the mailbox password path and a nonempty `HOMEPLANNER_TRUSTED_PROXY_IP`, and mounts the credential read-only. The runtime validates that the peer is an IP. With mail off, access requests are still recorded and reviewable in the admin queue (they require `HOMEPLANNER_TRUSTED_PROXY_IP`); only notification mail is skipped, and a one-line notice without secrets is logged at startup. Queued outbox rows accumulate unsent until mail is enabled. Enabling mail starts an outbox worker immediately: pending entries can be sent on startup and an interrupted send can be retried. Review the queue and delivery plan before enabling it. The mailbox is authorized, but its credential is not available; do not enable or test real delivery until separately provisioned and reviewed.

## Ingress and proxy trust

`compose.ingress.yaml` attaches web, alias `homeplanner-web`, to the existing external `homeplanner_ingress` network and removes the example host port. Caddy's own persistent attachment and current configuration remain separately managed; the overlay does not change Caddy. The overlay preserves web's database and outbound networks. Compare against the actual current host definition and network membership before use; only Caddy and HomePlanner web should be on that ingress. Database stays isolated, without a host port. Compose implementations must support `!reset` for the port removal; inspect the merged result before use.

For public requests, set `HOMEPLANNER_TRUSTED_PROXY_IP` to the exact address seen by the web socket as Caddy's peer on this network, not a subnet, client IP, host gateway guess or a public address. Caddy's `reverse_proxy` for this site must overwrite `X-Forwarded-For` with exactly one validated client IP; for a direct client-to-Caddy topology a reviewed `header_up X-Forwarded-For {remote_host}` is a candidate. If another proxy sits in front, stop and review its trust boundary first: `{remote_host}` would identify that proxy, not the end client. Do not trust client-supplied forwarding headers or comma-separated chains. Validate the complete Caddy config, including any global trusted-proxy settings, without disturbing other sites. Use a controlled synthetic client to send a forged `X-Forwarded-For` and demonstrate that the backend receives the actual client IP as one value; verify a direct non-Caddy peer is rejected and malformed/multiple addresses fail. Confirm the actual observed Caddy peer, exact ingress membership, TLS, public/private routes and Energy health separately. Do not record cookies or credentials.

Container IPs can change after Caddy or network recreation. Establish a reserved, stable peer address in the reviewed network configuration or reverify the address and update the web setting before enabling requests after every relevant recreation. A mismatch must leave requests unavailable or rejected; never widen trust to a network or accept arbitrary forwarded headers. Current topology and header behavior have not been verified by this local work.

The Stage 1 receipt describes the prior same-host drill, not an offsite backup. Complete the Stage 2 backup/restore remediation below before accepting a 006 rollout.
2. Select the accepted image by immutable local image ID via `HOMEPLANNER_WEB_IMAGE=sha256:...`; apply the same image to web and maintenance. `HOMEPLANNER_BUILD_CONTEXT` is still required for Compose rendering even when using a preloaded image: supply the reviewed sanitized context, and use `--no-build` when starting web. Validate the image ID, platform, UID and input manifest on the target; never rely solely on a mutable tag. Preserve deployed migration 001–005 bytes and compare their exact SHA-256 values against the database ledger before migration. Do not normalize bytes in the running database.
3. Provision the private files and confirm metadata and scoped role URLs without revealing contents. Save the complete reviewed effective Compose output privately, using `--env-file /dev/null` and **all** currently required overlays, including the existing provider overlay and, when reviewed, `compose.ingress.yaml`. Do not include `compose.mail.yaml` while its credential or trust gate is missing. Compare the resulting configuration with the current one, especially DB service, photo mount, locks, secrets, network, resource limits, provider connection version and validation registry. Use the actual existing project name and non-secret host path configuration; examples are not a substitute for a target-specific reviewed command.
4. Fence traffic, drain web, take the canonical operations lock, and establish a compatible recovery point. For an upgrade from 001–005, use the new image's standalone Compose maintenance wrapper to run `provision-access` **once before** `migrate`, then `verify`. For a fresh cluster run `provision`, then `provision-access`, `migrate`, and `verify`. For example, after setting the reviewed Compose file array `C` and enabling its operations profile: `"${C[@]}" --profile operations run --no-deps -T maintenance provision-access`, then the same command with `migrate` and `verify`. These jobs acquire the shared lock themselves; do not pre-hold it in a separate process for these invocations. Both provision jobs deliberately fail when any of their fixed role names already exist. On an interrupted run inspect roles, privileges and ledger before deciding what to do; never blindly rerun provisioning or replace credentials. No web startup applies migrations.
5. Recreate only HomePlanner web using the reviewed full configuration and immutable image (`"${C[@]}" up -d --no-build --no-deps web`); retain DB, photos, locks and existing unrelated services. With ingress still closed, verify image identity, secret mount metadata, readiness, operations and writer locks, ledger, role separation and mail-off request availability. Reattach the reviewed ingress only after the peer/header checks. Run public TLS, anonymous/private and authenticated acceptance separately and record Energy health without changing it. Include the existing provider overlay whenever it is part of the active configuration; do not accidentally remove its mount or validation settings.

## Recovery and rollback gate

The local candidate `backup.sh` holds the operations lock, stops web, locks the photo volume, checks the ledger's migration names and fences the three original logins plus any pair of new logins. A 006 ledger requires both new logins; a partial pair, unexpected login state or unsupported ledger stops the capture. It terminates those roles' sessions across databases and requires the application database to be quiescent. All privileged writers must also be excluded by the operator. After the encrypted database, photo archive and encrypted photo manifest are complete and any requested publication succeeds, it re-enables the fenced roles and restarts web only if web was originally running. An interrupted or failed capture may leave web stopped and logins fenced; inspect the exact state and incomplete artifacts before any manual recovery. Do not blindly restart or rerun. The script's ledger name check is not a checksum verification: compare the actual ledger hashes with the selected image separately. The current Stage 2 Compose candidate also interpolates the new role and rate-key paths during a five-entry backup even when those roles do not exist; resolve this with the actual host's reviewed configuration and private placeholder paths where appropriate, without provisioning or enabling new production roles merely to take a backup.

`restore-drill.sh` accepts a new isolated project and empty private photo destination. It inspects the encrypted archive's table-of-contents marker to choose the 001–005 or 001–006 role set, provisions the required roles atomically with **NOLOGIN** before loading the dump, and checks that the restored ledger and exact migration hashes match the selected image and the archive marker. It removes existing sessions, verification records, access and admin challenges and admin grants, disables model use and verifies photo hashes and UID 1000 access. A 006 restore requires all five disabled logins; a 001–005 restore requires only the original three. The current Compose wiring still requires paths for both new isolated password mounts even for a 001–005 restore: provide separate private fixture/recovery files, never production credentials, although those two roles are not created for that ledger. The two restore-specific variables are `HOMEPLANNER_RESTORE_ACCESS_PUBLIC_PASSWORD_FILE` and `HOMEPLANNER_RESTORE_MAIL_PASSWORD_FILE`. Restore roles must use independent isolated credentials, never production URLs or passwords.

Keep the restore network internal, without published ports or egress. An incomplete restore must remain isolated with web stopped; retain its project, destination and logs for inspection. The role provisioning transaction creates no enabled login even if a later load fails. Preserve budget reservations and other liabilities for reconciliation. The outbox is deliberately retained, including queued or uncertain messages: the mail login remains disabled, and no mail worker or mailbox credential is started by the drill. An accepted-but-unacknowledged message can be duplicated. Do not enable that login or start a mail worker until a **separate explicit reconciliation and activation decision** covers every queued, retrying and uncertain message and the intended delivery plan. Session, access and model reactivation likewise require their own review.

Optional local publication is a cooperative-owner Linux contract. Set `HOMEPLANNER_PUBLISH_INCLUDED_ROOT` to the canonical included root, `HOMEPLANNER_PUBLISH_ROOT` to its existing `homeplanner` child, and `HOMEPLANNER_BACKUP_ROOT` to that same child. Set `HOMEPLANNER_BACKUP_INVOCATION_NONCE` to a new, unpredictable 32-character lowercase hexadecimal value on every invocation. The publication parent must be owned by the invoking effective UID and mode `0700`; every ancestor must be root- or caller-owned, non-symlink, and not group/other writable. No path component may be hidden. The filesystem must enforce Linux modes, `renameat2(RENAME_NOREPLACE)` and file/directory fsync. Root and UID 1000 each work when their own parent and files have the stated ownership; a root-owned `0400` capture is not readable by a UID 1000 runner. Verify the actual target mount and execute capture and validation under the intended same account. Do not use the script as a privileged path-taking service.

Capture is created as `.incomplete-<nonce>` in that parent. The three ciphertexts, `SHA256SUMS` and visible `capture-manifest.json` are the exact inventory. Before sealing, the manifest records `READY`, nonce, final name, capture start/end epochs, the five- or six-name migration ledger, and SHA-256 values for all ciphertexts and `SHA256SUMS`. It records ledger names, not verified migration byte hashes. The publisher checks the inventory and hashes, changes files to `0400` and the directory to `0500`, fsyncs files and the directory, renames to `<UTC timestamp>-<nonce>` without replacement in the same parent, and fsyncs that parent. A crash or fsync failure can leave a visible but indeterminate final. No such directory is fresh merely because it exists or has a `READY` manifest.

The producer writes one `HOMEPLANNER_BACKUP_RECEIPT_V2 <nonce> <final-name> <start-epoch> <end-epoch> <manifest-sha256> COMPLETE` line to stdout only after publication, successful login restoration and successful web start command if web was originally running. `COMPLETE` is not service readiness. The caller captures the complete stdout in a private owner-only regular log, separately retains the exact child exit status, and must not manufacture a status or receipt after timeout. It invokes the validator after the child has exited, under the same UID and while retaining the outer shared run lock:

```sh
python3 -B deployment/validate-backup.py \
  --parent "$HOMEPLANNER_PUBLISH_ROOT" --nonce "$nonce" \
  --not-before "$invocation_start_epoch" --max-age "$max_age_seconds" \
  --process-status "$capture_status" --receipt-log "$private_capture_stdout"
```

On exit 0 stdout contains exactly five newline-delimited absolute **file** paths, in the order database, photos, photo manifest, checksum file and capture manifest. All path components are visible, and no control characters are permitted in the parent path. On any failure stdout is empty, stderr describes rejection, and the exit status is nonzero. The validator checks the child status, a single receipt, nonce, invocation lower time bound, capture age, clock ordering, exact final name, parent and capture ownership/modes, symlinks, filesystem, file types/link counts, exact inventory, checksums, manifest schema, ledger and receipt binding. The caller must preserve these exact output paths as individual restic source arguments; never pass the HomePlanner parent or a broad `consistent-data` source that recursively includes it. Do not assume `--files-from` overrides excludes. If the existing combined operation cannot avoid recursion, hosting may run a separate HomePlanner backup operation after Energy using the same existing outer lock, timer and repository. Preserve all existing non-HomePlanner sources and exclusions. Check the restic result and separately verify actual snapshot contents and restore; validation does not establish offsite success.

The outer runner, not the producer, holds `run.lock` across capture, validation, Energy backup, any separate HomePlanner operation and applicable repository check. Keep its own descriptor alive while the child uses FD 9 for the distinct HomePlanner operations lock; do not reacquire the shared lock in the producer. On capture, validation or HomePlanner backup failure, continue the existing Energy backup/check independently, record component results and last-success times separately, alert and return nonzero. Preserve all prior complete captures; select only the current nonce-bound successful capture for this run, with no freshness claim for older captures. No automatic local deletion, forget or prune is added; retention needs a separately reviewed policy. Inspect phase-dependent web/login state after failure and never automatically unfence, start mail, or enable model use.

These checks assume a trusted cooperative owner, protected ancestors and all participating writers honoring the outer lock until restic finishes. They detect changes at validation points but do not prevent a same-owner or administrator chmod, mutation or path swap between validation and restic's later opens; `0500`/`0400` is not WORM. A root or same-owner adversary, already-open writable descriptors, actual host power loss and production filesystem durability are outside this contract. Independent enforcement, target filesystem behavior, service readiness, real shared-job integration and offsite restore remain separate gates.
The existing encrypted StorageBox/restic destination is the selected candidate where compatible. Its actual job coverage, schedule, shared-lock coordination, receipt handling and key recovery must be verified separately before claiming offsite protection; a shared destination alone proves none of them. The proposed 120-second capture and 30-second TERM grace are planning values, not measured limits. An interrupted capture can leave web stopped and logins fenced; the isolated TERM test does not establish a hard downtime bound or crash recovery. Preserve the original rate key and private configuration securely where the recovery plan can recover them, together with the database, photos and encrypted artifacts. Test an independently stored encrypted recovery copy and key recovery separately. Local synthetic drills and same-host snapshots do not establish offsite protection or authorize production recovery.

Migration 006 changes the ledger and the earlier image rejects a 006 database. An image-only rollback after 006 is not valid. Keep traffic closed and follow an independently reviewed recovery plan using a compatible image, or restore a verified pre-006 database and matching photos/configuration with explicit accounting for changes since the snapshot. Never overwrite a current shared Caddy configuration with a stale whole-file backup; reconcile its HomePlanner block and preserve the bound inode and other sites. Fail closed and retain evidence on any mismatch.

## Stage 2 activation and rollback

Migration 006 enforces access approval **as soon as it commits**: the replaced actor check and the restrictive row-level policies on designs and photos apply to every session at once. Run it only inside a maintenance window with ingress closed.

**Rollback is restore-only.** There is no down-migration. The previous image refuses a database whose ledger contains 006, so the only way back is to restore a verified pre-006 snapshot (database plus photos) taken inside the same window, losing any later writes. Keep traffic closed until acceptance passes, and confirm the restore procedure for that snapshot before migrating.

Pre-checks, before migrating live:
1. The owner's admin binding must match exactly one Google account: `SELECT count(*) FROM hp_private.admin_binding b JOIN hp_auth.account a ON a."userId"=b.user_id AND a."providerId"='google' AND a."accountId"=b.google_subject` must return 1. Any other value means the owner is not seeded; stop.
2. List design owners other than the bound owner; each of them loses access until approved.
3. Take the verified pre-006 database and photo snapshot.

Post-check, before traffic reopens: `SELECT count(*) FROM hp_private.access_entitlements WHERE provenance='verified-owner-binding' AND status='approved'` must return 1.

Recovery if that count is 0: keep ingress closed to everyone else, open `/admin.html`, sign in with the owner's Google account and complete the admin verification; the owner seed (`seedOwner`) runs from there. Re-run the post-check. If it still fails, restore the pre-006 snapshot.

Access requests are recorded and appear in the owner's approval queue at `/admin.html` whether or not mail is enabled; they need only `HOMEPLANNER_TRUSTED_PROXY_IP` for rate limiting. Mail is an optional notification add-on.
