# HomePlanner VPS operations (implementation hold)

This is a local deployment design, not authorization to change the server. Rollout is on **hold**: the last reported free space is 48 GiB, below the 60 GiB floor, and the other owner's archive-first cleanup is NO-GO. Do not access or change the Energy application, its networks, data, containers or backups. Review the pending storage-completion contract and independently verify all gates before operating this stack.

The intended stack is an isolated Node service, Better Auth with Google, dedicated PostgreSQL and a private filesystem. The application starts with empty public starter data; local data is never automatically uploaded. It does not require a managed database or hosting platform.

## Current implementation boundary

`HOMEPLANNER_ENABLE_RUNTIME=0` is the default. It serves only the static artifact and an unhealthy readiness endpoint; private handlers are not configured. When explicitly enabled, the executable composes the real photo service and storage maintenance with separate least-privilege pools, requires the process-held volume lock and a successful first maintenance pass, and gates photo operations on maintenance health. Startup fails closed when these checks fail. This integration is local and still requires the storage owner's completed verification, native Linux tests and independent review before any rollout. The model provider is unconfigured; no provider credential is supplied by this Compose file.

The web entrypoint holds an exclusive Linux `flock` on `.homeplanner-writer.lock` in the private photo volume using descriptor 9 inherited by Node. The lock remains held for the process lifetime, including its in-process maintenance. The production composition checks the inherited descriptor and that another open cannot acquire the lock; loss or replacement triggers process exit. Backup and restore drain the app and take the same inode's lock before touching photos. This is advisory: all writers must use it, privileged host operators must never delete or replace the lock, and a local Linux filesystem with working `flock`, hard links and directory fsync is required. Do not share this volume through an unverified network filesystem or allow unrelated writers. Native Linux contention, process termination and restart tests are a release gate; source inspection and Windows tests do not establish those properties.

Before a future deployment, provision a dedicated volume directory as root, owned by root and not writable by group or others (for example mode `0711`). In it pre-create `.homeplanner-writer.lock` as a regular file writable by UID 1000 (for example UID 1000, mode `0600`), and a `data` directory owned by UID 1000 with mode `0700`. The application can write under `data` but cannot unlink or replace the lock inode because the parent is root-owned. The host mount source `HOMEPLANNER_PHOTO_DIR` is this volume root, not `data`. Operators preparing an isolated restore must make a separate directory with the same layout and an empty `data`. Verify the volume-to-lock mapping and permissions on the actual host; do not weaken the parent permissions to make startup work.

## Build from reviewed input only

Use Node 24 and the lockfile. From the checkout, run `node scripts/prepare-hosting.mjs --vps <new-outside-checkout-directory> <separate-new-manifest-file>`. The output contains only the exact paths in `scripts/vps-manifest.mjs`, including all runtime, auth/session, SQL migration, photo service, API and static-build inputs. It creates a deny-by-default `.dockerignore`; the separate manifest records SHA-256 hashes. It rejects symlinks, pre-existing destinations and detected source changes. Run `node scripts/audit-vps-context.mjs` **inside the new input directory**, compare its manifest with the reviewed release and inspect it before building. Never point Compose at the checkout: private seed data, photos, `.git`, environment files and evidence must not enter the context.

`HOMEPLANNER_BUILD_CONTEXT` is that absolute sanitized directory. `deployment/compose.yaml` references its `deployment/Dockerfile`. The image uses Node `24.22.2-bookworm-slim` and PostgreSQL `17.11-bookworm` pinned to multi-platform index digests. Their [official Node image tags](https://hub.docker.com/_/node/tags?name=24.22.2-bookworm-slim) and [PostgreSQL release notes](https://www.postgresql.org/docs/release/17.11/) were checked when preparing this design; recheck patches and digests at release. Build installs locked build dependencies, produces and audits the 21-file public artifact, then installs separate production dependencies. The final app runs as UID/GID 1000, has a read-only root and bounded temporary filesystem, drops capabilities, and has bounded CPU, RAM, PIDs and logs. The Compose app tag `homeplanner-web:local` is a mutable build-time label; a release must capture and deploy a reviewed immutable app image digest and retain a compatible rollback image. Native Sharp installation, resulting image contents/layers and dependency inventory still need a real clean Linux build and inspection.

The database has an internal-only network, a dedicated named volume and no published port. The web also has an outbound network for identity and any separately approved provider. This is not an OS disk quota: the photo store accounts for all bytes under its root and rejects admission below 60 GiB free; independent filesystem quotas and alerts require host review. DB, backup, image and log growth must be monitored separately. The resource limits are initial values, not measured production sizing.

## Explicit configuration and jobs

Compose substitution values are supplied by the operator, without a repository `.env`: `HOMEPLANNER_BUILD_CONTEXT`, `HOMEPLANNER_PHOTO_DIR`, `GOOGLE_OAUTH_CLIENT_ID`, and the following external absolute **file paths**: `HOMEPLANNER_DB_BOOTSTRAP_PASSWORD_FILE`, `HOMEPLANNER_MIGRATION_DATABASE_URL_FILE`, `HOMEPLANNER_AUTH_DB_PASSWORD_FILE`, `HOMEPLANNER_APP_DB_PASSWORD_FILE`, `HOMEPLANNER_PHOTO_MAINTENANCE_DB_PASSWORD_FILE`, `HOMEPLANNER_AUTH_DATABASE_URL_FILE`, `HOMEPLANNER_APP_DATABASE_URL_FILE`, `HOMEPLANNER_PHOTO_MAINTENANCE_DATABASE_URL_FILE`, `HOMEPLANNER_AUTH_SECRET_FILE`, `HOMEPLANNER_CSRF_SECRET_FILE`, `GOOGLE_OAUTH_CLIENT_SECRET_FILE`. Provision and secure these independently on the future host; do not place their contents in source, evidence, images or logs. Local Compose file-backed secret mounts retain host permissions: ensure the app UID 1000 can read only its required mounts, and separately restrict operator and database secrets. Do not assume Swarm secret permission behavior.

Inside the app, the corresponding paths are `/run/secrets/auth_database_url`, `app_database_url`, `photo_maintenance_database_url`, `auth_secret`, `csrf_secret`, and `google_client_secret`; `HOMEPLANNER_ORIGIN=https://home.appelbaums.com`, `HOMEPLANNER_PHOTO_VOLUME_ROOT=/var/lib/homeplanner/photos`, `HOMEPLANNER_PHOTO_ROOT=/var/lib/homeplanner/photos/data`, `HOMEPLANNER_MIN_FREE_BYTES=64424509440`, and `HOMEPLANNER_DIST=/app/dist-vps`. The URLs must use the Compose-local host `db`, database `homeplanner`, default port 5432, no query parameters and the respective login `hp_auth_login`, `hp_app_login`, `hp_photo_maintenance_login` or, for the migration URL only, `homeplanner_bootstrap`. This also prevents an isolated restore job from selecting a different host through its URL. Auth and CSRF secrets must be independent, persistent, high-entropy values of at least 32 bytes. Runtime reads settings only on explicit configured startup, from a named environment value or its `_FILE` alternative, never both. The Google client is configured for the exact origin and `/api/auth/callback/google`.

Provision the empty dedicated database with the one-shot maintenance service, explicitly `docker compose -f deployment/compose.yaml --profile operations run --rm maintenance provision`, then `... run --rm maintenance migrate`. `provision` fails if any of its eight fixed role names already exist; it creates no-login owner/runtime roles and distinct auth/app/photo-maintenance logins, with no superuser or bypass-RLS privilege. The migration identity requires the authority to create schemas and set the owner roles. Provision and migration are separate operations; investigate a partial failure before retrying. Migrations have a checksum ledger and are **never** run by web startup. The bootstrap/migration credential must not be mounted into web. After restoring a database, roles belong to the isolated database cluster and must be separately provisioned before restoring objects.

## Proxy and network proposal

The supplied Compose file publishes `127.0.0.1:3107` for a host-side proxy only. A Caddy container's `127.0.0.1` is its own namespace, so that binding is not a reachable container upstream. One possible future route is `home.appelbaums.com { reverse_proxy web:3107 }` after attaching Caddy to a **dedicated HomePlanner ingress network** shared only with web, confirming the actual network alias and checking reachability. Another option is a verified host-gateway address with a deliberately reachable host binding and firewall rules. Either requires an actual topology and port check, approval, and a reviewed Compose/Caddy change; neither is applied here. Never attach HomePlanner to Energy's application or database networks, and never assume a host-loopback upstream works from a container.

## Backups and isolated restore

`bash deployment/backup.sh` is a proposed app-only cold backup. It requires an approved operations window, no concurrent privileged database maintenance, an external `HOMEPLANNER_OPERATIONS_LOCK` shared by all HomePlanner operators, `HOMEPLANNER_EXCLUSIVE_OPERATIONS=yes`, an existing private absolute `HOMEPLANNER_BACKUP_ROOT`, an available GPG public recipient specified as `HOMEPLANNER_BACKUP_RECIPIENT`, and the Compose inputs above. It stops/drains only HomePlanner web, acquires the photo volume's actual lock, disables all three runtime database logins, terminates their remaining sessions, rejects other active DB sessions, and streams the DB custom dump, photo tar and NUL-delimited file checksums directly through GPG encryption. The resulting ciphertexts have a separate `SHA256SUMS`. It restores login ability and the prior web running state only after successful capture. Failures leave state for operator investigation; never blindly resume. All privileged DB operators must honor the same operations lock: a superuser can bypass application controls. Validate the dedicated volume, recipient and filesystem capacity before use. Ciphertext hashes detect corruption but are not signatures or proof of authenticity. Define retention, encryption-key recovery, monitoring and an independently approved offsite destination later; none is configured here.

`bash deployment/restore-drill.sh <absolute-backup-directory>` targets only a new `HOMEPLANNER_RESTORE_PROJECT` named `homeplanner-restore-...`, a new private `HOMEPLANNER_RESTORE_PHOTO_DIR` volume root with a pre-created lock and empty `data`, and an isolated internal PostgreSQL network with no published ports. It requires separate external `HOMEPLANNER_RESTORE_DB_PASSWORD_FILE`, `HOMEPLANNER_RESTORE_MIGRATION_URL_FILE`, `HOMEPLANNER_RESTORE_AUTH_PASSWORD_FILE`, `HOMEPLANNER_RESTORE_APP_PASSWORD_FILE`, `HOMEPLANNER_RESTORE_PHOTO_MAINTENANCE_PASSWORD_FILE`; these must address the isolated `db` service, not the live DB. It refuses existing project containers/volume and overlapping live/restore photo paths; it stops/drains web and holds both photo locks. It checks ciphertext hashes, provisions fresh cluster roles, restores the DB, revokes sessions, verification tokens, admin challenges and grants, disables all three app logins and model use, verifies the migration ledger, restores only validated regular paths into the empty photo directory, and compares file hashes to the encrypted manifest and active ready DB rows. On failure retain the isolated resources and partial destination for inspection. This is not an in-place production restore or a complete reconciliation of every pending, orphaned or quarantined row: the storage completion owner must supply that validation.

The initial lifetime budget is USD 25; a verified administrator can revise it up to the existing USD 10,000 implementation guard without resetting recorded or ambiguous liabilities. The snapshot preserves the recorded budget ledger as of backup time; it cannot contain later spending. Do not supply provider credentials or enable model use after restore until an authorized owner has conservatively reconciled all post-backup liabilities without erasing recorded or ambiguous amounts. Fresh login is required after restore. A successful drill, owner/count verification and measured RPO/RTO are required; no backup or restore was executed against a live system in this work.
