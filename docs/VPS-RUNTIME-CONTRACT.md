# VPS runtime contract

Status: standalone implementation. Node binds 0.0.0.0:3107 inside the container; supplied Compose exposes only host loopback. Runtime defaults to unconfigured/unready. HOMEPLANNER_ENABLE_RUNTIME=1 composes verified database, authentication, private photo storage and maintenance adapters. Provisioning/migration remain explicit jobs, never automatic web startup work.

## Identity and browser requests

The application uses the same origin for the site and API. The identity owner configures the pinned Better Auth instance with a fixed public base URL, Google only, verified provider subject, PostgreSQL-backed sessions, no cookie cache, a seven-day absolute session expiry with refresh disabled, and host-only Secure, HttpOnly, SameSite=Lax cookies. Do not accept forwarded host or scheme from the client. The router invokes the pinned `better-auth/node` adapter through `createBetterAuthHandler(auth)` and sends it an unread bounded byte stream before application JSON parsing. Its auth surface is limited to POST `/api/auth/sign-in/social`, GET `/api/auth/callback/google`, and POST `/api/auth/sign-out`. Other library endpoints, including its session response, are not public. The fixed external origin must be configured by the integration owner, never derived from request headers.

`GET /api/session` returns exactly `{ userId, sessionId, displayName, csrfToken }` or 401/503. Both IDs are lower-case UUIDs. `userId` is the internal app identity. `sessionId` is a separate non-secret, random generation identifier for that particular live session; it must never be a cookie value, session token, OAuth token, digest usable as a credential, email or user ID. The resolver verifies the actual cookie and queries current session state for every request; it must not consume the request body. Unknown, expired, revoked or switched sessions fail closed. The browser must treat either ID changing as a generation change, cancel pending work, revalidate on focus/pageshow and broadcast account changes across tabs.

Unsafe app requests, including sign-out and raw PUT, require an exact `Origin` equal to the fixed origin, `X-HomePlanner-Session: <sessionId>`, and `X-HomePlanner-CSRF: <csrfToken>`. Missing or foreign Origin is rejected, even with valid cookies. Foreign Origin on safe API requests is rejected too. An outdated expected ID returns 409 `session_changed`; a missing or incorrect CSRF value returns 403. The server computes the CSRF value as a base64url HMAC-SHA256 over a domain separator and the session ID, using a separately provisioned secret of at least 32 bytes. Its entropy, protected provisioning, persistence and rotation are the identity owner's responsibility. It is available through the same-origin session response, is not an authentication credential, and becomes invalid on session change, secret rotation or logout. Login initiation has no session-bound token, but still requires exact Origin and the library's own checks; the OAuth callback is the explicitly allowed GET exception. Browser code uses same-origin cookies, never bearer tokens or token persistence. `Authorization` headers are rejected by this host.

The session ID check is a concurrency guard, not identity verification. All writes must use the server-resolved identity, and C must repeat live-session and reservation/fence checks immediately before publishing an uploaded object. A response from an old frontend generation must be discarded even if the server committed before logout.

## Route and adapter contract

The explicit routes and methods are in `runtime/routes.cjs`; unknown API and file paths return 404 without a fallback to the checkout. Dynamic IDs are lower-case UUIDs supplied as `req.query.id` and `req.query.photoId`; query parameters cannot override IDs or be duplicated. `existingHandlers(deps)` adapts the revised handlers with Node `req.query`, parsed `req.body`, `res.status`, `res.json`, header and binary response expectations. B's composition supplies the database and identity adapters; C's filesystem handlers are separate. The runtime refuses bearer headers. Production composition remains blocked on the storage safety and completion gates in `HOSTING.md`.

`createRuntime({ origin, dist, integrations })` accepts the fixed origin, public artifact directory, and trusted in-process integrations. Integrations comprise `csrfSecret`, `resolveSession(req)` returning `{ userId, sessionId, displayName }` or null, `authHandler`, `handlers` keyed by the route names, `ready()` returning true only after migrations and required services are ready, and optional `close()` for pools and other resources. Resolver or health exceptions fail closed. Unconfigured mode does not load service secrets; the explicitly enabled entry point loads the reviewed composition and its external runtime configuration. The integration must only use a reviewed configured instance and must keep provider/database secrets out of logs and artifacts. Readiness additionally checks that the resolver, auth handler, and every explicit route handler are supplied. Liveness and readiness return only status, without configuration details. `stop()` stops accepting work, allows up to ten seconds for socket draining, closes remaining connections, then awaits all accepted dispatch tasks before invoking the integration close hook. There is no application deadline on that final task wait; external forced process termination remains a crash-recovery path. Timeouts and body limits remain enforced even for chunked input.

JSON requests are UTF-8 objects. The default network cap is 1,100,000 bytes; proposals are 65,536 bytes and small photo/admin bodies 4,096 bytes. The existing handlers retain their own narrower semantic limits. JSON is bounded before parsing. Auth input is capped at 65,536 bytes without reading it before the library adapter. The raw route has a 10 MiB network ceiling; both declared length and streaming bytes are checked. HTTP timeout, interrupted request, oversize input, invalid JSON and unavailable integrations cannot dispatch a successful business operation. API responses use private/no-store and safe error envelopes; status, ETag, If-Match and idempotency behavior remains the responsibility of the business handlers.

## Photo reservation and upload

A successful reservation returns exactly `{ photoId, expiresAt, uploadUrl, contentType, maxBytes }`, validated by `uploadReservation` in `shared/schema/vps-v1.json`. `uploadUrl` is a relative `/api/designs/<designId>/photos/<photoId>/raw`; it must match the captured design and photo IDs, with no origin, bucket or storage key. `contentType` is JPEG, PNG or WebP; `maxBytes` is 1 through 10 MiB, and the client checks expiry. The PUT sends the raw bytes and reserved content type with the same cookie, Origin, CSRF and captured session ID; it is not JSON or base64. Completion remains the readiness authority.

The C handler is provided as `handlers.photoRaw({ req, stream, session, params })`. It must consume only `stream`, enforce the reservation's tighter size, MIME and hash, stage bytes privately with backpressure, and return `{ status, body, headers }` only after the stream ends. It must not trust IDs from the body or publish incomplete, oversized, expired, switched-session, deleted or fenced uploads. The handler owns immutable atomic publication, durable receipts, cleanup fencing, physical capacity, failure recovery and rechecking session/reservation under the shared photo/design lock. The router provides the transport seam; it does not implement the filesystem protocol.

## Build and release boundary

`npm run build:vps` and `npm run audit:vps` create/check the exact allowlist in `shared/vps-public-files.json`. The VPS artifact uses empty starter data, the self-hosted Better Auth browser bundle and no hosted-provider SDK or public provider keys. The client has been ported, but private controls cannot operate until the server integrations and release gates are complete. `npm run build` and `npm test` retain the earlier hosted build solely for transition. The earlier hosted dependency is a development dependency only; neither the intended VPS runtime nor its public artifact requires it. Old source and tests do not demonstrate VPS acceptance.

`node scripts/prepare-hosting.mjs --vps <new-outside-checkout-directory> <separate-manifest-file>` copies only `VPS_INPUTS`, creates a deny-by-default context ignore file and records content hashes, rejecting symlinks and existing destinations. Audit the prepared context with `scripts/audit-vps-context.mjs` and review its manifest before building. The storage completion module and migration are included; their owner verification and independent audit of the final context and Linux image/layers remain required. Do not copy `house-data.js`, personal photos, secrets, evidence, `.git`, or arbitrary checkout content. No secrets belong in the checkout, prepared input or public artifact.

Pinned direct dependencies: Better Auth 1.7.18 and pg 8.23.1; the schema CLI is the matching `auth` 1.7.18 development dependency. Better Auth's [PostgreSQL documentation](https://better-auth.com/docs/adapters/postgresql) supports a `pg` pool and describes a dedicated schema; its [CLI documentation](https://better-auth.com/docs/concepts/cli) describes configuration-based schema generation and checks; its [session documentation](https://better-auth.com/docs/concepts/session-management) documents disabling refresh. The [Node integration example](https://better-auth.com/docs/integrations/next) requires mounting the adapter before body parsing. These are library integration references, not evidence that the application has a configured or accepted live authentication flow.
